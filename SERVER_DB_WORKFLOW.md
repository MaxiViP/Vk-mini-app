# Регламент работы с проектом через серверную БД

## 1. Главный принцип

Любая работа с БД в этом проекте должна идти не против локальной MySQL, а против серверной базы через SSH-туннель.

Точка входа:

```powershell
ssh -L 3306:127.0.0.1:3306 admin@195.140.146.86
```

После поднятия туннеля локальный адрес `127.0.0.1:3306` становится мостом к серверной MySQL.

## 2. Обязательный preflight перед любыми правками

1. Поднять или проверить SSH-туннель.
2. Убедиться, что порт доступен:

```powershell
Test-NetConnection 127.0.0.1 -Port 3306
```

3. Проверить, что backend использует `back/.env`.
4. Проверить, что `DATABASE_URL` в `back/.env` указывает на туннель и на правильную базу `chat-app`.
5. Помнить, что `back/.env.example` не является источником истины.

## 3. Что считать правильной целевой конфигурацией

- `DATABASE_URL` должен вести на серверную MySQL через локальный порт туннеля.
- Для этого проекта нельзя автоматически предполагать, что `localhost` или `127.0.0.1` означает локальную БД на компьютере.
- Если туннель поднят, это адрес удаленной БД.

Пример смысловой схемы:

```text
Локальный backend -> 127.0.0.1:3306 -> SSH tunnel -> 195.140.146.86 -> MySQL -> database chat-app
```

## 4. Безопасная последовательность работы для будущих задач

1. Сначала понять, затрагивает ли задача:
   - Prisma schema
   - migrations
   - env
   - backend API
   - frontend API contract
2. Проверить туннель и `DATABASE_URL`.
3. Только после этого запускать backend, Prisma-команды или диагностику БД.
4. После изменений перепроверять не только код, но и фактический сценарий на серверной схеме.
5. Если поведение подозрительно "слишком работает", помнить про fallback-логики.

## 5. Команды, которые обычно допустимы

Из корня:

```powershell
npm run dev
```

Только backend:

```powershell
npm run dev --workspace=back
npm run start --workspace=back
```

Только frontend:

```powershell
npm run dev --workspace=front
npm run build --workspace=front
```

Prisma:

```powershell
npm run prisma:generate --workspace=back
```

Если уже есть готовые migration-файлы и их нужно применить к серверной БД:

```powershell
npx prisma migrate deploy
```

Запускать это имеет смысл только после проверки туннеля и `DATABASE_URL`.

## 6. Что нельзя делать по умолчанию

- Нельзя молча переводить проект на локальную MySQL ради удобства.
- Нельзя считать `127.0.0.1:3306` локальной базой без проверки туннеля.
- Нельзя бездумно запускать `prisma migrate dev` против серверной БД.
- Нельзя коммитить реальные секреты из `back/.env` и `front/.env.*`.
- Нельзя полагаться на fallback-режимы как на признак исправной прод-схемы.

## 7. Как работать с Prisma в этом проекте

### Если нужно просто синхронизировать клиент Prisma

```powershell
npm run prisma:generate --workspace=back
```

### Если нужно применить уже существующие миграции к серверной БД

```powershell
cd back
npx prisma migrate deploy
```

### Если нужно менять схему

1. Сначала изучить `back/prisma/schema.prisma`.
2. Проверить текущие миграции в `back/prisma/migrations`.
3. Осознанно сформировать изменение схемы.
4. Перед применением к серверной БД повторно проверить туннель и `DATABASE_URL`.
5. После применения проверить реальные ручки:
   - `/health`
   - `/api/billing/summary`
   - `/api/llm/models`
   - `/api/workspace/me`

## 8. Что обязательно помнить про fallback-логику

Если БД недоступна или схема старая, часть системы может не упасть явно:

- OTP может уйти в in-memory mode.
- Phone auth может выдать dev-style fallback result.
- Workspace может отдать временные fallback-данные.
- Billing и usage могут уйти в legacy schema mode.
- OAuth может сработать через fallback profile.

Вывод:

- Ответ от API еще не доказывает, что серверная БД реально используется правильно.
- Для диагностики всегда надо отделять "ручка отвечает" от "ручка реально работает на нужной серверной схеме".

## 9. Мини-чеклист после любых изменений

1. Туннель поднят.
2. `DATABASE_URL` смотрит в серверную БД `chat-app`.
3. Backend стартует без ошибок Prisma.
4. `/health` отвечает.
5. Ключевые ручки не ушли в fallback-режим.
6. Если менялась схема, проверена совместимость billing/usage/workspace/auth.
7. Секреты не попали в git diff и в `.md` файлы.

## 10. Короткая памятка для будущих сессий

```text
Перед любыми действиями с БД в этом проекте нужно считать серверную MySQL единственным источником истины.
Локальный адрес 127.0.0.1:3306 используется как SSH-туннель к серверу, а не как локальная база.
Сначала проверить туннель и back/.env, потом уже запускать backend, Prisma и тестовые сценарии.
Особенно внимательно относиться к fallback-логикам: они могут скрывать проблемы с подключением к БД или недокатанные миграции.
```
